## 练习 1 — colex 手算

```
L = (3,5):(5,1)
```

**1. `L(2,4)` = 14**

多维坐标直接内积：`2*5 + 4*1 = 14`。

**2. `L(7)` = 7**

单个整数要先按 colex 展开。Shape 是 `(3,5)`，第一个 mode 大小 3：

```
7 -> (7 % 3, 7 / 3) = (1, 2)
```

再求值：`1*5 + 2*1 = 7`。

常见错误是按 row-major 想成 `(7/5, 7%5) = (1,2)` —— 这次**碰巧**也是 `(1,2)`，答案一样。换成 `k=4` 就分道扬镳了：colex 给 `(1,1) -> 6`，错误的想法给 `(0,4) -> 4`。所以别用巧合验证规则。

**3. `size(L)` = 15，`cosize(L)` = 15**

`size = 3*5 = 15`。`cosize` = 最大输出 + 1 = `L(2,4) + 1 = 15`。两者相等说明这个 layout 紧密无洞。

## 练习 2 — 三步法设计 B

```cpp
// step1  A = (6,8):(8,1)  ->  L_0 = 1, L_1 = shape_0 = 6
// step2  row 步进 1 -> 1*L_0 = 1 ; col 步进 1 -> 1*L_1 = 6
auto B = make_layout(make_shape(Int<2>{}, Int<4>{}), make_stride(Int<1>{}, Int<6>{}));
// step3  base = A(2,4) = 2*8 + 4*1 = 20
const int base = 20;
```

结果 `A∘B = (2,4):(8,1)`，`base + (A∘B)(i,j) == A(2+i, 4+j)` 全部 8 点成立。

**关键点：`L_1 = 6` 不是 4。** 逻辑基来自 **A 的 Shape 第一个 mode**（这里 A 有 6 行），跟正文里 4 行的例子不同。把这个数字记成"4"是最常见的错误。再强调一次：逻辑基只由 Shape 决定，与 Stride 无关。

**为什么起点要单独加？** `composition` 只表达线性映射，没有常数项 —— Layout 本身表达不了"从偏移 20 起"。真实代码里这个偏移由 **Tensor 的指针**承担（`tensor.data() + 20`，或更常用的 `local_tile` 直接返回带偏移的 view）。这是 Section 02 的内容。这里手工加是为了让你看清：**形状（B）和起点（base）是两件独立的事。**

## 练习 3 — 反向算 A∘B

`A = (4,8):(8,1)`，`L = (1,4)`，`A_stride = (8,1)`。

| # | B | 定位 | 越界检查 `delta*s ≤ shape_m` | 结果 |
|---|---|---|---|---|
| 1 | `2:4` | `d=4=1·L_1` → m=1, delta=1 | `1×2=2 ≤ 8` ✓ | `_2:_1` |
| 2 | `4:2` | `d=2=2·L_0` → m=0, delta=2 | `2×4=8 > 4` ✗ **越界** | `(_2,_2):(_16,_1)` |
| 3 | `2:8` | `d=8=2·L_1` → m=1, delta=2 | `2×2=4 ≤ 8` ✓ | `_2:_2` |
| 4 | `(2,4):(4,1)` | 逐 mode 独立 | 见下 | `(_2,_4):(_1,_8)` |

**第 2 题是重点。** 如果只套"stride = delta × A_stride[m] = 2×8 = 16"，会得到扁平的 `4:16` —— 错。要先查越界：mode0 只有 4 格，而 `delta=2, s=4` 意味着要取逻辑下标 `0,2,4,6`，其中 4 和 6 **已经溢出 mode0**（mode0 只覆盖 0-3）。所以分裂成 `(2,2)`：mode0 内取 2 个（下标 0,2 → 偏移 0,16），再跨到 mode1 取 2 个（+1）。

对照 `A ∘ 2:2`：`delta=2, s=2`，`2×2=4 ≤ 4` 刚好不越界 → 扁平的 `_2:_16`。**一个数之差，结果形态完全不同。**

第 4 题逐 mode 算：`mode0: 2:4` → `d=4=L_1`, delta=1 → `1×1=1`；`mode1: 4:1` → `d=1=L_0`, delta=1 → `1×8=8`。拼成 `(2,4):(1,8)` ✓。

**后半题（取偶数行 × 全部列）：**

```cpp
auto B = make_layout(make_shape(Int<2>{}, Int<8>{}), make_stride(Int<2>{}, Int<4>{}));
```

- 第一维走**偶数行**：row 每次 +2 → `2 × L_0 = 2×1 = 2`
- 第二维走**全部列**：col 每次 +1 → `1 × L_1 = 1×4 = 4`

结果 `A∘B = (2,8):(16,1)`，`A∘B(i,j) == A(2i, j)` 全部成立。

**对照记忆：** 取偶数**列**是 `(4,4):(1,8)`（第二个 stride 翻倍），取偶数**行**是 `(2,8):(2,4)`（第一个 stride 翻倍）。哪一维要跳步，就在哪一维的"步进数"上乘 2。

## 练习 4 — 预测 coalesce

真实结果：

| # | 输入 | 结果 | 判据 |
|---|---|---|---|
| 1 | `(2,4):(4,1)` | `(_2,_4):(_4,_1)` | `4*2=8 != 1` → **合不了** |
| 2 | `(2,4):(1,2)` | `_8:_1` | `1*2=2 ✓` → 合并 |
| 3 | `(4,2):(1,4)` | `_8:_1` | `1*4=4 ✓` → 合并 |
| 4 | `(2,3,4):(1,2,6)` | `_24:_1` | `1*2=2 ✓`, `2*3=6 ✓` → 全合并 |
| 5 | `(2,3,4):(1,2,8)` | `(_6,_4):(_1,_8)` | `1*2=2 ✓`, 但 `2*3=6 != 8` → **部分合并** |

**第 4 与第 5 的差别 —— 这是本题的重点。**

第 4 题 stride `(1,2,6)`：

```
mode0: shape 2, stride 1  ->  覆盖 0,1
mode1: shape 3, stride 2  ->  2*1=2 == stride[1] ✓  前两维并成 6:1，覆盖 0-5
mode2: shape 4, stride 6  ->  6*1=6 == stride[2] ✓  再并成 24:1，覆盖 0-23
```

严丝合缝，完全连续 → 塌成一维 `24:1`。

第 5 题 stride 改成 `(1,2,8)`：

```
前两维照样并成 6:1 (覆盖 0-5)
mode2: stride 8，但前两维只铺满到 6  ->  6 != 8，中间空了 2 个 (6,7)
```

所以只能合并到 `(6,4):(1,8)` —— **部分合并**。这也说明 `coalesce` 是逐维贪心推进，遇到断点就停，而不是全合或全不合。

第 5 题正好是真实 GPU 代码里的常见形态：`(6,4):(1,8)` 就是"每行 6 个有效元素，行距 8"，即 **padded 数组**。`coalesce` 保留了这个结构，等于告诉你"行内连续、跨行有洞"，正是判断能否向量化的依据（可以按 6 个一组向量化，不能跨行）。

## 练习 5 — complement 的含义

真实结果：

| 输入 | 结果 | 补集在补什么 |
|---|---|---|
| `complement(4:1, 16)` | `_4:_4` | L 铺满 0-3，补集负责**跨组**（步长 4，跳到 4/8/12） |
| `complement(4:4, 16)` | `_4:_1` | L 只碰 0,4,8,12，补集负责填**组内**（步长 1，补 0-3） |
| `complement(2:1, 16)` | `_8:_2` | L 铺满 0-1，补集跨组（步长 2），需要 8 组才够 16 |

规律：`size(L) * size(complement) == N`，且两者的 stride 互补 —— **L 密则补集疏，L 疏则补集密**。complement 自动算出"哪里还空着"。

**第 2 题的完整 layout：**

```cpp
auto full = make_layout(make_layout(Int<4>{}, Int<4>{}),      // 4:4
                        complement(...));                     // 4:1
// full = (4,4):(4,1)
```

分配方式：

```
thread 0 拿到:  0  1  2  3
thread 1 拿到:  4  5  6  7
thread 2 拿到:  8  9 10 11
thread 3 拿到: 12 13 14 15
```

不重不漏覆盖 0-15 ✓。

**这个分配模式值得记住**：每个线程拿**连续 4 个** —— 这是 "thread-contiguous" 布局，适合每线程做向量化读（一次 `int4`），但相邻线程访问的地址相隔 4，**跨线程不合并**。

对比第 1 题 `4:1` + 补集 `4:4` = `(4,4):(1,4)`：

```
thread 0 拿到: 0 4  8 12
thread 1 拿到: 1 5  9 13
```

每个线程拿**跨步的 4 个**，但同一轮里 4 个线程访问 0,1,2,3 —— **跨线程连续，合并访存**。

**这两种恰好是 GPU 上最重要的一组取舍**：per-thread 向量化 vs 跨 thread 合并访存。后面 TiledCopy 的 thread-value layout 设计，核心就是在这两者间权衡。complement 是你手里构造它们的工具。

## 练习 6 — 嵌套 mode

`AN = ((4,2),4):((8,1),2)`

**1. 层次查询**

```
rank(AN)    = 2      仍是 2 个 mode（不是 3）—— 嵌套不增加 rank
size(AN)    = 32     元素总数
size<0>(AN) = 8      第 0 个 mode 的整体大小 = 4*2
```

`rank` 数的是**顶层** mode 个数。`((4,2),4)` 顶层有两个：`(4,2)` 和 `4`。

**2. `AN(6,1)` 的嵌套坐标 = `AN((2,1), 1)`**

mode0 的 shape 是 `(4,2)`，内部按 colex 展平：`flat = i0 + 4*i1`。反解 `flat=6`：

```
i0 = 6 % 4 = 2
i1 = 6 / 4 = 1
```

验证：`AN(6,1) = AN((2,1),1) = 19` ✓。

**这说明嵌套是"可选的精度"**：你可以继续用扁平坐标（老代码不用改），也可以用嵌套坐标显式指定子 mode（需要区分层次时用）。

**3. `coalesce(AN) = (4,8):(8,1)` —— 正是 A 本身**

说明**嵌套只是表示形式，映射本身没变**。`AN` 和 `A` 是同一个函数的两种写法：`AN` 保留了"这个 mode 由两段拼成"的结构信息，`coalesce` 把它压成最简形式。

有用的推论：想检查两个 layout 是否等价，比较 `coalesce` 后的结果。

**4. `composition(A, (2,16):(4,1))` 会产生嵌套**

推理：逐 mode 独立算。

- `mode0: 2:4` → `d=4=L_1`, m=1, delta=1，`1×2=2 ≤ 8` ✓ 不越界 → `2:1`
- `mode1: 16:1` → `d=1=L_0`, m=0, delta=1，但 `1×16=16 > 4` ✗ **越界** → 分裂

实测：`(_2,(_4,_4)):(_1,(_8,_1))` —— 嵌套出现在**第二个** mode 上。

对比正文里 `(8,4):(1,8)` 的嵌套在第一个 mode。**规律：嵌套出现在哪个位置，取决于 B 的哪个 mode 越界，与 A 无关。**

## 练习 7 — capstone 的 PADDING


**1. 实测（2048×2048 `int`，H200）**

`PADDING = 1` 已达 ~2467 GB/s。改成 2 或 4 不会再有明显提升，可能略降（smem 用量变大，occupancy 略降）。

**2. 为什么 `PADDING = 1` 就够**

smem 有 **32 个 bank，每个 4 字节**，地址 → bank 的映射是 `(byte_addr / 4) % 32`。对 4 字节的 `int`，就是 `element_index % 32`。

转置时读 smem 是**沿列方向**走，32 个线程访问的元素下标是：

```
tile(0,c), tile(1,c), tile(2,c), ...   即 0*stride+c, 1*stride+c, 2*stride+c, ...
```

地址间隔就是 `stride` 个元素。

- `stride = 32`（无 padding）：所有线程的 `index % 32` **全等于 `c % 32`** → 32 个线程挤在同一个 bank → **32-way conflict**，串行 32 次。
- `stride = 33`：第 i 个线程落在 `(33i + c) % 32 = (i + c) % 32` → 32 个线程恰好铺满 32 个不同 bank → **零 conflict**。

只要 `stride` 与 32 **互质**就能完全错开，而 33 是最小的这种值。加更多 padding 不带来额外好处，只是浪费 smem。

**3. 换成 `double`（8 字节）**

`double` 占 2 个 bank。相邻元素的 bank 号差 2，所以 32 个线程只能覆盖 16 个 bank —— **`double` 的列访问天生就有 2-way conflict，padding 消不掉**。

`PADDING = 1`（stride 33 个 double = 66 个 bank 宽）时，线程 i 的起始 bank 为 `(66i + 2c) % 32 = (2i + 2c) % 32`，全是偶数 → 只用 16 个 bank，**2-way conflict**。

想彻底消除需要换思路，例如：
- 用 XOR swizzle 而不是 padding（CuTe 有 `Swizzle<B,M,S>`，Section 04 会用到）
- 或者把 `double` 当成两个 `int` 分开搬

这题的意义在于：**padding 是针对"元素大小 ≤ bank 宽度"的技巧，不是万能药。** 这也正是 CuTe 提供 `Swizzle` 作为一等公民的原因。
