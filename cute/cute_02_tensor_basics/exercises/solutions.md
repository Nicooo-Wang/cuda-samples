## 练习 1 — Tensor 基础

`T = (4,6):(6,1)`，底层 `v[24]` 值 0-23。

```
T(2,3) = 15        offset = 2*6 + 3*1 = 15
size(T) = 24       4*6
rank(T) = 2

T(1,_) = (_6):(_1)     首元素 6     第 1 行 -> 6,7,8,9,10,11
T(_,2) = (_4):(_6)     首元素 2     第 2 列 -> 2,8,14,20
```

**两个切片的对比很说明问题：**

- `T(1,_)` 是取一行。行内连续，所以 stride 为 1。
- `T(_,2)` 是取一列。列方向每次跨一整行，所以 stride 是 6（原 layout 的行距）。

两者的 rank 都从 2 降到 1，起点分别落到指针上（偏移 6 和 2）。

## 练习 2 — view 语义

```
T(3,5) = -1.0f   ->   v[23] = -1      offset = 3*6+5 = 23
r = T(3,_); r(5) = -2.0f   ->   v[23] = -2
```

**两次都写穿到了底层数组。** 切片不是拷贝，`r` 和 `T` 和 `v` 指向同一块内存，只是索引方式不同。

这条性质是 CuTe kernel 能层层切分的基础：`local_tile` 取块、`local_partition` 分线程，全都是零拷贝的 view 变换。如果每次切分都要拷贝，GPU 上根本没法用。

**反过来也要小心：** 两个 view 若覆盖范围重叠，写其中一个会影响另一个。partition 之所以要保证"不重不漏"，原因就在这里（见练习 4）。

## 练习 3 — local_tile

`BT = (8,12):(12,1)`，值 0-95，切成 `(4,4)`。

**1. 块数 = 6**

`(8/4) × (12/4) = 2 × 3 = 6`。

**2. `local_tile(BT, (4,4), (1,2))` 首元素 = 56**

手算：块坐标 `(1,2)` 对应原矩阵起点 `(1×4, 2×4) = (row 4, col 8)`，偏移 `4×12 + 8 = 56` ✓。

**3. layout = `(_4,_4):(_12,_1)`，与 `(0,0)` 块完全相同**

这是 `local_tile` 最重要的性质：**所有块的 layout 一致，区别只在指针。** 因为块内的走法（行距 12、列距 1）跟块在哪没关系。

好处很实际：kernel 里处理每个块的代码可以完全一样，`blockIdx` 只影响 `local_tile` 那一行。

**4. `zipped_divide(BT, (4,4)) = ((_4,_4),(_2,_3)):((_12,_1),(_48,_4))`**

嵌套结构 `((块内), (块号))`：

| 部分 | 值 | 含义 |
|---|---|---|
| mode0 shape `(4,4)` | 块内 4×4 | 一块多大 |
| mode0 stride `(12,1)` | 行距 12、列距 1 | 块内怎么走 |
| mode1 shape `(2,3)` | 2×3 = 6 块 | 一共几块 |
| mode1 stride `(48,4)` | row 方向跳 **48**、col 方向跳 **4** | 块与块之间怎么走 |

**mode1 的 stride 是关键：**
- `48 = 4 行 × 行距 12` —— 往下一块要跨过 4 整行
- `4 = 4 列 × 列距 1` —— 往右一块要跨过 4 列

验证：块 `(1,2)` 的起点 = `1×48 + 2×4 = 56` ✓ 和第 2 问一致。

**这正是 Section 01 §3.4 讲的嵌套 layout 的实际用途。** `local_tile(BT, tile, coord)` 就是"把 mode1 固定成 `coord`，留下 mode0"。

## 练习 4 — thr_layout 决定分配模式

32 个元素（值 0-31）：

**(1) `thr = 8:1`（8 个线程，连续编号）**

```
tid0:  0  8 16 24
tid1:  1  9 17 25
tid2:  2 10 18 26
```

每线程 4 个，**跨步 8**。同一轮里 8 个线程访问 0-7 —— **跨线程连续 = 合并访存**。这是想要的。

**(2) `thr = 8:4`（stride 写错）**

```
tid0:  0  8 16 24
tid1:  0  8 16 24     <- 和 tid0 完全相同
tid2:  0  8 16 24
```

**8 个线程全部拿到同一批元素。** 24 个元素从没被访问，4 个被重复写 8 次。

这就是**有问题的那个（答案：2）**。而且它**不报错、不警告**——编译通过、跑起来不崩，只是结果错。

为什么？`thr_layout` 的 stride 决定"线程 t 的起点在哪"。`8:4` 意味着起点是 `4t`，但 complement 算出的 value 步长也是 8，两者撞车，覆盖范围退化了。

**记住：`thr_layout` 的 stride 通常取 1。** 这是 partition 最常见也最难查的错误。

**(3) `thr = 4:1`（只有 4 个线程）**

```
tid0:  0  4  8 12 16 20 24 28
tid1:  1  5  9 13 17 21 25 29
```

线程少了一半，每线程从 4 个元素变成 **8 个**。分配依然正确（不重不漏），只是每人干的活翻倍。

**规律：`每线程元素数 = 总元素数 / 线程数`**，且 `local_partition` 会自动算好——这正是 Section 01 §4 的 complement 在做的事。

## 练习 5 — 两级范式

`BT = (8,8):(8,1)`，值 0-63。

**1. `local_tile(BT, (4,4), (0,1))` 首元素 = 4**

块坐标 `(0,1)` → 原矩阵起点 `(0, 4)` → 偏移 `0×8 + 4 = 4` ✓。这个块覆盖 row 0-3 × col 4-7。

**2-3. `local_partition(blk, (2,2):(2,1), 3)` → tid3 拿到 `13 29 15 31`**

推导：`blk` 的 layout 是 `(4,4):(8,1)`，起点在元素 4。thr_layout `(2,2):(2,1)` 表示 2×2 共 4 个线程，tid3 对应线程坐标 `(1,1)`。

partition 后 tid3 的起点：块内 `(1,1)` → 偏移 `1×8 + 1×1 = 9`，加上块起点 4 = **13** ✓。

之后每个线程在两个方向各拿 2 个，步长是"线程数 × 原步长"：
- 行方向：`2 线程 × 行距 8 = 16` → 13, 29
- 列方向：`2 线程 × 列距 1 = 2` → 13→15, 29→31

按遍历顺序 `(0,0)(1,0)(0,1)(1,1)` 得到 `13 29 15 31` ✓。

**这就是完整的两级范式**：`local_tile` 定位到块（CTA 层，对应 `blockIdx`），`local_partition` 定位到线程（thread 层，对应 `threadIdx`）。两级都是纯 view 变换，零拷贝。

后面每一章的 kernel 骨架都是这个形状，只是中间插入 Copy（Section 03/04）或把最内层换成 MMA（Section 05/06）。

## 练习 6 — make_fragment_like

`mine` 的 layout 是 `(_2,_2):(_16,_2)`。

```
make_fragment_like(mine) = (_2,(_2)):(_1,(_2))

frag: size = 4,  cosize = 4
mine: size = 4,  cosize = 19
```

**1-2. 为什么 stride 不同？**

`mine` 的 stride `(16,2)` 是**指向大数组的跨步**——它是从 8×8 矩阵里 partition 出来的 view，元素散落在原数组各处。

`make_fragment_like` 要新开一块**独立的**小缓冲，没必要跨步，所以换成紧密排布，第一维 stride = 1。这样最利于向量化和寄存器分配。

**3. cosize 的差距（4 vs 19）才是重点。**

- `frag` 的 `size == cosize == 4`：4 个元素占 4 个连续地址，**紧密无洞**。
- `mine` 的 `size = 4` 但 `cosize = 19`：只有 4 个元素，却横跨 19 个地址的范围（最远元素在偏移 18）。

**说明什么？** `cosize` 告诉你"这个 view 需要多大的地址空间"。`mine` 是散落在大数组里的窗口，`frag` 是独立的一小块。

**实际意义：** 编译器只能把 `cosize` 小且紧密的 Tensor 放进寄存器。`mine` 那种跨度 19 的 view 必须留在原内存。所以做累加器时一定要用 `make_fragment_like` 新开，不能直接拿 partition 的结果当累加器。

Section 05 的 MMA 累加器就是这么来的。

## 练习 7 — 改 capstone

**1. 基线（M=4096, N=512，H200）**

```
v0 baseline                 0.1461 ms   57.4 GB/s   1.00x
v1 cute naive               0.1447 ms   58.0 GB/s   1.01x
v2 cute + smem              0.1425 ms   58.9 GB/s   1.03x
v3 cute + tile/partition    0.1434 ms   58.5 GB/s   1.02x
```

四版几乎完全一样。**这本身就是结论：CuTe 的抽象是零开销的。** GEMV 是纯访存瓶颈（A 的每个元素只用一次，没有复用），瓶颈在带宽，跟怎么写下标无关。

（你自己跑的绝对值会不同——这台机器 GPU 是共享的。看相对关系即可。）

**2. 改成 (512, 4096) 之后**

M 变小意味着 grid 从 16 个 block 降到 2 个——**GPU 严重欠占用**，所有版本都会变慢，且差距被放大。

受影响最大的是 **v2/v3**：它们把 x 放进 smem，而 x 的长度就是 N。N 从 512 涨到 4096，smem 用量翻 8 倍，每个 SM 能驻留的 block 数下降（occupancy 降低），加载 x 的开销也从"分摊到 4096 行"变成"分摊到 512 行"——**摊薄效应消失了**。

这引出一个通用判断：**缓存只在复用次数够多时才划算。** v2/v3 加载 x 的成本是 O(N)，收益是省下 M 次重复读——M 越小越不划算。

**3. smem 容量**

```
N = 512    ->  512 × 4B  = 2 KB       没问题
N = 4096   ->  4096 × 4B = 16 KB      够用（上限 ~228KB），但 occupancy 已受影响
N = 65536  ->  65536 × 4B = 256 KB    超了! 编译就会失败
```

H100/H200 每 block 的 smem 上限约 228KB（需要 `cudaFuncSetAttribute` 显式提升，默认只有 48KB）。

**怎么改？分段加载（tiling over K）：**

```cpp
for (int k0 = 0; k0 < N; k0 += TILE_N) {
    // 只把 x 的 [k0, k0+TILE_N) 段搬进 smem
    // 累加这一段的贡献
    __syncthreads();
}
```

把 N 维切成若干段，每次只缓存一段。**这正是所有 GEMM kernel 处理 K 维的方式**——Section 06 会看到完整版本。

值得注意的是：这个"分段"用的就是 `local_tile`，tiler 只切一个维度（README §3 最后提到的用法）。**练习里学的工具，到真实 kernel 里原样复用。**
